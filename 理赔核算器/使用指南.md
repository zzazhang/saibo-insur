# 使用指南

## 先回答一个常见疑问：保单是预加载的，会不会用不了新保单？

**保单库确实是预加载的**（`claims_calc/data/policies.json`，当前 10 款），
**但工具没有被这 10 款锁死**。处理一份不在库里的新保单，有三条路：

| 路线 | 适用场景 | 要不要动保单库 | 能否用结算层 |
| --- | --- | :---: | :---: |
| 一、加进保单库 | 这份保单要反复用、要做对照 | 要 | ✅ |
| 二、在案例里内联保单 | 临时算一单，不想动库 | 不要 | ✅ |
| 三、不指定保单 | 只想核定损失，不管赔多少 | 不要 | ❌ |

三条路都实测通过。下面逐条说。

---

## 路线三：不指定保单（最简单，等同原版行为）

不写 `policy_id`，工具就退回到原版的行为：只算第①层事实口径损失，
第③层结算不启用。

```json
{
  "categories": { "F1": { "switch": "ON" } },
  "items": { "F1-01": { "params": { "p1": 200, "p2": 1500 } } }
}
```

想手工控制哪些科目计入，加 `"coverage_mode": "manual"`，然后逐项写
`"include": "OFF"`。这就是原版 Web 端的用法，一点没变。

---

## 路线二：在案例里内联保单（推荐用于临时算单）

把保单直接写进案例 JSON 的 `policy` 字段，**不需要改保单库、不需要改任何代码**。
引擎优先读 `policy`，读不到才去库里找 `policy_id`。

```json
{
  "case_id": "TEST-01",
  "case_name": "某新条款临时测算",
  "coverage_mode": "policy",
  "policy": {
    "id": "my-new-policy",
    "name": "某财险公司网络安全保险（2026版）",
    "insurer": "某财产保险股份有限公司",
    "product_type": "综合型",
    "parameters_are_assumed": true,

    "coverage": {
      "default": "unmapped",
      "categories": {
        "F1": "covered",
        "F2": "covered",
        "S1": "covered"
      },
      "items": {
        "S3-01": {
          "status": "nominal_only",
          "clause": "第十三条",
          "note": "条款承保赎金但附「在中国法律允许范围内」限定语"
        }
      }
    },

    "settlement": {
      "aggregate_limit": 3000000,
      "deductible": { "scope": "per_occurrence", "amount": 80000 },
      "bi": {
        "deductible_mode": "higher_of",
        "deductible": 80000,
        "max_indemnity_days": 90
      },
      "sublimits": [
        { "id": "SL-A", "name": "响应与恢复费用",
          "items": ["F1", "F2"], "limit": 800000, "shares_aggregate": true }
      ]
    }
  },

  "categories": { "F1": { "switch": "ON" }, "S3": { "switch": "ON" } },
  "items": { "F1-01": { "params": { "p1": 200, "p2": 1500 } } }
}
```

跑：

```bash
python -m claims_calc.cli run cases/你的案例.json
```

### coverage 只需要写不一样的地方

映射的优先级是 **精确科目 > 大类默认 > 全局兜底**，所以不必写满 69 项：

- `default` 设成 `"unmapped"`（条款没提到的一律不赔），是最保守也最安全的起点
- `categories` 按大类批量声明（`"F1": "covered"` 一行搞定 F1 下全部 11 项）
- `items` 只写需要偏离大类默认的个别科目，顺便记条款出处

承保状态六档：

| 状态 | 含义 | 计入 |
| --- | --- | :---: |
| `covered` | 条款明确承保 | ✓ |
| `limited` | 有限承保 / 需特约 | ✓ |
| `conditional` | 附条件承保（须事先同意、须用指定机构等） | ✓ |
| `excluded` | 条款明确列为责任免除 | ✗ |
| `nominal_only` | 条款字面列明，但国内实践不可赔 | ✗ |
| `unmapped` | 条款中没有对应责任项 | ✗ |

### settlement 全是可选的

不写就是不限额、不免赔。只写你知道的那部分即可：

| 字段 | 不写会怎样 |
| --- | --- |
| `aggregate_limit` | 不封顶 |
| `deductible` | 不扣免赔额 |
| `sublimits` | 无分项限额 |
| `bi.deductible_mode` | 默认 `waiting_only`（只扣等待期） |
| `bi.max_indemnity_days` | 赔偿期不设上限 |
| `conditional_deductible` | 无条件免赔额 |

## 路线一：加进保单库（要反复用就走这条）

编辑 `tools/build_policies.py`，在文件末尾照现有 10 款的写法加一个字典，
然后加进 `ALL_POLICIES` 列表，重新生成：

```bash
python tools/build_policies.py
```

**为什么是改 Python 脚本而不是直接改 JSON**：判断依据（这一项为什么判承保、
依据哪一条）写在可读的 Python 注释里能留得住；直接手搓 JSON 三个月后就看不懂了。
`policies.json` 是生成物，不要手改。

加完之后自动可用：

```bash
python -m claims_calc.cli list                        # 会出现在列表里
python -m claims_calc.cli mapping 你的保单id --out x.md  # 导出 69 项责任对应表
python -m claims_calc.cli compare 某案例.json --policies 你的保单id,pingan-cyber-b
```

Web 端的「投保产品」下拉也会自动出现，无需改前端。

## 从零处理一份新保单的完整流程

1. **读条款，填 coverage**。逐个大类问「这款保单管不管这类损失」，
   只对个别科目做例外。重点盯四处：
   - 赎金条款有没有「在中国法律允许范围内」之类的限定语 → `nominal_only`
   - 行政罚款有没有类似句式 → 目前 69 科目无对应位置，须文字记录
   - 外包商责任是承保还是除外
   - 有没有营业中断责任，是按天还是按小时、毛利率还是净利润

2. **填 settlement**。条款里的限额数字通常写「由投保人与保险人协商确定」，
   没有公开数字，按演示值设定并把 `parameters_are_assumed` 置为 `true`。

3. **确认 BI 口径**，这是最容易出错的地方：

   | 条款怎么写 | `deductible_mode` |
   | --- | --- |
   | 只有等待期，没有 BI 免赔额 | `waiting_only` |
   | 只有免赔额，没有等待期概念 | `deductible_only` |
   | **「免赔额与等待期自留额取较高者」** | `higher_of` |
   | 二者叠加扣减 | `both` |

   第三种最常见（苏黎世 6.3、泰康第八条第四款、国寿财B 第 14.1 节都是），
   **填错会算错几万到几十万**。

4. **口径不一致怎么办**。若条款按小时计、以净利润为基础（如国寿财B款），
   不要改 `formulas.py`，用填参约定表达：
   `p1` 填日均净利润、`p2` 填中断小时数÷24、`p3` 填免赔期间小时数÷24、
   `p4` 固定填 `1.0`、`p5` 填 `1 −(实际净利润÷应得净利润)`。
   **务必在案例的争议点里写明该约定**，否则参数含义会被误读。

5. **跑一遍并检查告警**：

   ```bash
   python -m claims_calc.cli validate cases/新案例.json   # 结构校验
   python -m claims_calc.cli run cases/新案例.json         # 跑数
   python -m claims_calc.cli audit cases/新案例.json -v    # 参数来源审计
   ```

   告警要逐条看，尤其这几类：
   - `未落入任何分项限额组` → 分项组配少了
   - `同时命中多个分项限额组` → 分项组的 items 有重叠，会重复封顶
   - `行内填写了「赎金分项限额」…请留空` → 保单参数漏进了事实层

## 常用命令速查

```bash
python -m claims_calc                                   # 启动 Web (127.0.0.1:8765)

python -m claims_calc.cli list                          # 保单库
python -m claims_calc.cli sources                       # 参数来源库
python -m claims_calc.cli mapping <保单id> --out x.md    # 69 项责任对应表

python -m claims_calc.cli validate cases/*.json         # 结构校验
python -m claims_calc.cli run cases/*.json              # 批量跑数
python -m claims_calc.cli run cases/*.json --md out/    # 导出 Markdown 报告
python -m claims_calc.cli audit cases/*.json -v         # 参数来源审计
python -m claims_calc.cli compare 案例.json --policies a,b  # 同一事故多保单对照

python tools/build_policies.py                          # 重建保单库
python tools/build_parameter_sources.py                 # 重建参数来源库
python tools/build_summary.py                           # 重建十案汇总

python -m pytest tests/ -q                              # 101 个测试
```

## Web 端怎么用

```bash
python -m claims_calc
```

浏览器打开 http://127.0.0.1:8765/ ，三步走：

1. **案件与损失项** — 先在「投保产品」下拉里选保单（选完各科目的计入开关会
   按条款责任映射自动填好），再勾选本案涉及的损失模块
2. **参数填写** — 每个科目标题旁有承保状态徽标，鼠标悬停能看到条款出处与理由
3. **结果报告** — 三层口径 + 保单结算过程 + 已核定但不予赔付的科目清单

右上角还有：案例库（存取 `cases/` 目录）、导入/导出案例 JSON、导出 Markdown 报告。

**注意**：Web 端目前只能从下拉里选已入库的保单，内联保单需要走案例 JSON。
如果临时算单需求多，可以考虑给前端加一个「粘贴保单 JSON」的入口。
